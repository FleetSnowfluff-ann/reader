# Upstream research and Phase 1 decisions

Reviewed 2026-10-19 (Asia/Shanghai). Sources are upstream README files, LICENSE files, package manifests, architecture/data-format docs, and GitHub commit feeds. No repositories were merged or installed. Only small individual source/documentation files were read in the cloud. Maintenance observations are a dated snapshot, not a support guarantee; commit frequency alone is not a quality metric.

## Architecture decision

Use a static ES-module app with one pinned PDF.js distribution. Separate PDF rendering, geometric text extraction, explicit alignment, translation transport, annotation/backup validation, and IndexedDB storage. Reuse our earlier original prototype as a small starting point, not any of the seven applications. No model, backend, paid API, cloud database, native shell, or second PDF library is required.

Translate only through manual entry, imported explicit links, or a user-consented HTTPS adapter. Machine-provided links remain uncertain until reviewed. Geometry connects an extracted sentence to the source page, but is not evidence that its Chinese translation is semantically correct. Cross-page fragments remain visible and flagged; a user may explicitly link loaded source IDs from adjacent pages. Never automatically splice unrelated fragments or overwrite the source PDF.

License boundaries: retain PDF.js's Apache-2.0 license in every build. The other projects are research references only; no AGPL/MIT/Apache application code or assets from them are included. Future reuse must re-check the exact file and dependency licenses, retain required notices, and satisfy any source-sharing obligations. This is a technical reuse decision, not legal advice.
